# Architecture

No build step: plain ES modules served as-is by Firebase Hosting.

```
index.html              page shell (markup only, plus a one-line script that applies a saved light theme before first paint). Holds the mount points that live outside #view: #toast-region and the #modal dialog
assets/logo.svg         the Tape mark; coloured by the theme tokens (see Theme), so one file serves both modes
favicon.svg             app icon, same mark as the logo; follows the OS light/dark setting (it sits in the browser's UI, not the page)
firebase-config.js      your Firebase project values
src/
  main.js               wiring: state -> render, delegated events, cloud sync
  store.js              the single state object + set()/subscribe()
  lib/                  pure logic, no DOM: format, parser, engine (fills -> trades), stats, fees, events (market-events file: validation, lookups), time (New York time -> the viewer's zone),
                        insights (bucket analysis), account (account value series, returns, axis ticks), daySummary (a day's or week's totals and trades, and the neighbouring trading days, for the calendar modals), workbooks (calendar/insights -> sheets), xlsx (sheets -> .xlsx bytes)
  services/cloud.js     the only file that knows about Firebase (also the shared market events and the admin flag)
  services/download.js  saveFile(): hands a string/bytes to the browser's download flow
  services/notify.js    notify({tone,title,text}): shows a toast in #toast-region (timing, pause on hover, dismiss)
  components/           generic UI: props in, HTML string out (LineChart mounts into an element)
  views/                one file per tab; each returns { html, mount? } from the current state.
                        calendarModal.js is the exception: not a tab, it holds the calendar's two modals (a day, a week row) and returns { title, body, nav?, actions? }
  styles/               tokens -> base -> components -> responsive (load order matters)
```

**Rules that keep it modular**
- `lib/` imports nothing from the DOM or Firebase, so it can be reused or tested on its own.
- Components never read the store; everything arrives as props. The same Panel, DataTable, Chips, Pager, MonthGrid or LineChart works in any other screen or project.
- Views only read state and return markup. Changes to state happen in `main.js` through `set()`.
- Markup carries `data-*` hooks only; `main.js` handles all events by delegation.
- To change backend, replace `services/cloud.js` and keep its shape: `createCloud(config,{onUser,onSettings,onLogs,onEvents,onAdmin,onError,onSaveError}) -> {signIn,signOut,saveLogs,saveSettings,saveEvents}`. `onEvents` and `onAdmin` are optional extras: if they can't be read (say the rules aren't deployed yet) the app carries on without them and never shows the "Access denied" screen, which is reserved for the person's own data. `saveEvents` returns its promise because the upload screen has to know whether it worked; the other saves report failures through `onSaveError`.

**Exports:** `[data-export="calendar|insights"]` builds a workbook with `lib/workbooks.js` and downloads it via `lib/xlsx.js` + `services/download.js`; `[data-export-log="<id>"]` downloads one stored log (`name` and `txt` from the Firestore snapshot) as-is. Add a new export by writing a `fooWorkbook(...) -> {name, sheets}` in `lib/workbooks.js` and an `ExportButton` in the view.

**Modal:** one native `<dialog id="modal">` in `index.html`, outside `#view`. `render()` rebuilds `#view` on almost every state change and would destroy a dialog inside it, so the modal has its own mount and `renderModal()` in `main.js` keeps it in sync with `st.modal` (`{kind:'day'|'week', key}` or `null`). Opening is `set({modal:{...}})` from a `[data-day]` or `[data-week]` button on the calendar (a week's key is `FIRST..LAST`, the first and last day of that row inside the displayed month, so the week modal always agrees with the Week cell). Closing is `closeModal()`, reached from the X and Close buttons (both `[data-modal-close]`), Esc, and a backdrop click that also *started* on the backdrop. Closing puts focus back on the day or week that opened it. If the data behind it disappears (another device deletes the log, or you sign out) it closes itself. Views build the content as `{title, body, nav?, actions?}` and `components/Modal.js` wraps it: `nav:{prev,next,noun}` adds header arrows (`[data-modal-go]`; left/right arrow keys do the same unless you are typing) and `actions` are buttons beside Close (`Share day`, `Open in Trades`). Phones get a full-screen sheet (`100dvh`, safe-area padding, header and footer pinned, page scroll locked, fields kept at 16px so iOS doesn't zoom).

*Re-rendering an open modal.* Content is only replaced when the markup actually changed, and `swapModal()` keeps the person's place: scroll position (reset when the day changes), and for any control marked `data-focus`, its focus, caret and unsaved text. This matters because saving a note echoes back from the cloud and re-renders the app. `syncModal()` records the markup after a note is saved so that echo doesn't rebuild the dialog at all. Whatever is being typed is saved (its `change` event) before the dialog closes, on Esc, or when you step to another day (`flushModal()`). Never call `set()` per keystroke inside the modal.

**Day notes:** the day modal's tags and note live in the same notes map as trade notes, under the key `day:YYYY-MM-DD` (it can't collide with a trade key, which is `date|symbol|time`). The shared handlers read `[data-note-key]` and fall back to the expanded trade (`st.exp`) for the Trades tab; a day left with no text and no tags is deleted from the map. Notes are capped at 2,000 characters and tags at 40 (`maxlength`), because the whole map is one Firestore document (1 MiB). Calendar days that have a note show a small marker.

**Toasts above the modal:** `#toast-region` is a `popover="manual"` so it lives in the browser's top layer; an open modal `<dialog>` is also top layer and would otherwise cover every toast, including "Couldn't save". `services/notify.js` re-opens the popover to sit above a modal that opened later.

**Market events and the admin:** one JSON document, `shared/events` (`{v:1, updated, events:[...]}`), holds scheduled releases (CPI, PPI, PCE, jobs, JOLTS, GDP, FOMC decisions and minutes) and market closures and early closes. Everyone signed in can read it; only the admin can write it. The admin is whoever has a document at `admins/{their uid}`, created **by hand in the Firebase console**: the rules allow no writes to `admins` from the app, and a user can only read their own entry. **Never keep an admin flag inside `users/{uid}`**: its owner can write that document, so anyone could make themselves admin. `isAdmin` in the store (and the controls it shows) is cosmetic; the rules are the enforcement. The rules can only check the top level (keys, `v == 1`, at most 3,000 events), so `lib/events.js` `validateEvents()` is the real gate: strict shape, real dates, allowed kinds and statuses, https-only urls, titles capped at 120 characters, no unknown fields, no duplicates, 800 KB limit. Treat an uploaded file as hostile and **escape every event string wherever it is displayed**. Event times are New York wall-clock times; `lib/time.js` `fromMarketTime()` shows them in the viewer's zone (`Intl`, 24-hour, daylight saving handled; Israel time if the browser can't say). The Settings page shows everyone a one-line status (hidden until something is uploaded), and the admin gets the controls from `components/MarketEvents.js`: choose a file, a preview of what validation found, then **Replace events**, which swaps the whole document and is visible to everyone at once. **Download current file** returns a file that can be edited and uploaded again.

**Empty states:** a signed-in person with no uploaded file still gets the whole app: `render()` hides `#view` and `#toolbar` only until the user and their data have loaded. Each view decides for itself what "no data" looks like. Dashboard, Insights, Trades (and Calendar, when it has neither trades nor market events) return `Empty({view, files, open})` from `views/shared.js`: with no files that is `components/EmptyState.js` with per-tab copy and a **Choose file** button (`[data-pick-file]`, which `main.js` wires to the `#file-input` rendered inside it); with files but no closed trade it is the older plain "No closed round trips yet" panel. Settings and Calendar need no trades to be useful, so they render normally. While a file is dragged over the page `main.js` puts `is-dragging` on `<body>` and the empty state lights up; dropping works anywhere on the page, empty state or not.

**Adding a tab:** create `views/foo.js` exporting `foo(ctx) -> { html }`, add it to `VIEWS` and `TABS` in `main.js`.
**Adding a component:** create `components/Foo.js` exporting a function that returns HTML, and its CSS block in `styles/components.css`.

**Naming conventions**
- Classes are descriptive kebab-case, named for what the thing *is* (`stat-card`, `calendar-day`, `chart-tooltip`), never abbreviations.
- Sub-parts are prefixed with their component (`stat-card-value`, `calendar-day-note`). State is an `is-*` class (`is-active`, `is-selected`, `is-gain`).
- Tone classes are `positive` / `negative`; `hide-on-phone` and `align-left` are the only utility classes.
- IDs exist only as mount points JavaScript looks up (`#view`, `#auth-gate`, `#trade-list`); styling hangs off classes.
- Colour and easing tokens live in `styles/tokens.css` (`--surface`, `--muted`, `--positive`, `--ease-out`).

**Motion rules** (see `styles/`): UI motion stays under ~250ms with `--ease-out`; transitions name their properties (never `all`); hover effects sit behind `(hover: hover) and (pointer: fine)`; frequent in-place updates render with `.is-static` so they never replay entrance animation; `prefers-reduced-motion` removes movement and keeps fades.

**Account value and funds:** `lib/account.js` turns trades plus `cfg.funds` (`{start, entries:[{id,date,type,amount,note}]}`) into the account-value series behind the dashboard chart. Return % is Modified Dietz (gain / starting value + time-weighted deposits), so deposits and withdrawals never count as profit. Funds are stored inside `cfg`, so the existing Firestore rules cover them unchanged. Value is realised P&L only (open positions are not marked to market).

**Header and account menu:** the header is one row at every width: logo left, `Add file` + avatar together on the right. `components/AccountMenu.js` renders the avatar button and dropdown (Sign out is a row inside it, wired through the existing `data-act="signout"`). Open/closed is the `.is-open` class on `#account`, toggled in `main.js`, so cloud-sync re-renders never close an open menu. The photo is the Google `photoURL` (https only, `referrerpolicy="no-referrer"`); if it fails to load it is removed and the initial underneath shows. The menu closes on outside click, Escape (focus returns to the avatar) and focus leaving it. The menu's first row is the **Dark mode** switch (`role="menuitemcheckbox"`, `data-theme-toggle`); its look is driven by `aria-checked`, which `main.js` keeps in sync because the menu is not rebuilt on a theme change (that would close it).

**Theme:** dark is the default, in `:root` of `styles/tokens.css`; light is `:root[data-theme="light"]`. The OS setting is deliberately ignored. The choice lives in `state.theme` (read from `localStorage` key `tape-theme` in `store.js`, written by the toggle in `main.js`), and `render()` mirrors it onto `<html data-theme>`. A saved light theme is also applied by the one-line script in `index.html`'s `<head>` so light never flashes dark; that is the only place theme logic lives outside `store.js`/`main.js`. Never hard-code colours: use the tokens, so a new screen works in both themes (the only exception is Google's own white sign-in button). Where the browser supports view transitions, the swap is a 180ms crossfade; otherwise it is instant.

**Logo and name:** the header shows `assets/logo.svg` followed by the site name (`.app-brand` > `.app-logo` + `.app-title`). The logo is referenced with `<use href="assets/logo.svg#logo"/>` rather than `<img>`: an `<img>` cannot see the page's CSS variables, so it would follow the OS theme instead of the in-app toggle. The file reads `--ink`, `--bg` and `--logo-accent` (with light-palette fallbacks, so it also renders on its own). `--logo-accent` exists so the mark keeps its designed green while `--positive` is tuned for text contrast. To change the logo, edit `assets/logo.svg` and `favicon.svg`; to rename the app, change `<title>`, `.app-title`, the `Gate` title in `main.js` (`SIGNED_OUT_GATE`), and the Google consent-screen name in `SETUP.md` step 3. The Firebase project id in `firebase-config.js` is an identifier, not a name; leave it.

**Toasts:** `services/notify.js` calls `components/Toast.js` and appends to `#toast-region` (an `aria-live="polite"` region that exists from page load). Use `notify({title, text})` for success and `notify({tone:'negative', title, text})` for failure; successes last 4s, failures 8s, hovering or focusing a toast pauses it, and at most 3 show at once. The close button is `[data-toast-close]`, handled in `main.js` with the other delegated events. An upload produces exactly one toast (`uploadToast()` in `main.js`), and failed cloud saves use `negative` toasts instead of `alert()`. Toasts animate with CSS transitions and `@starting-style` (not keyframes) so they can interrupt each other; they enter from below and leave the same way, faster.

**Chart hover:** `LineChart` shows only a line, a dot and a small label above them (the chart keeps an empty band at the top for the label, so it never covers the data). The dot is green above the baseline and red below it. One point (mouse hover, one finger) shows its date; comparing two (press-and-drag, two fingers) shows both dates and the change. The chart does not know about the page: it calls `onScrub(a, b)` on every move and `onEnd()` when the pointer leaves, and `views/dashboard.js` uses them to swap the big number and its change line (`.hero-scrub`) for the hovered values. The idle change lines and the hover line share one slot (`.hero-changes`), so nothing shifts. Dates are formatted with `toLocaleDateString('en-US', …)`, so they are English whatever the browser's language; the time is added only when the range is two days or less.

**Chart points are days:** on every timeframe except 1D the chart draws one point per calendar day that had a trade or a deposit/withdrawal, at the account value at that day's close (`dailyPoints` in `lib/account.js`), plus an opening point a day before the window so the first day has a line to climb from. On 1D each trade stays a point, because a single day would otherwise collapse to nothing. Grouping only changes what is *drawn*: the dashboard keeps computing every $ and % on the full per-trade series and maps each drawn point back to it (`ref`), so figures never depend on how the chart is sampled. To change the 1D rule, edit `daily=tf!=='1D'` in `views/dashboard.js`.

**Share card:** an expanded row in the Trades tab has **Share trade** and, when that day had more than one trade, **Share day**. Each makes a 1080x1350 PNG in the "Midnight" design: a trade shows entry, exit, shares and hold time; a day shows the day's net, W/L count and a mini list of its trades (first four in time order, then "+N more trades"). `lib/tradeCard.js` builds what a card says (`tradeCardModel`, `dayCardModel`: one shape, formatted like the table, trade facts only, never balance or email), `lib/cardDraw.js` draws any such model onto any 2D canvas context, and `services/cardImage.js` is the only part that touches the browser. The drawing is plain canvas, no library. The card reads the live CSS colour tokens (`--surface`, `--ink`, `--muted`, `--positive`, `--negative`) when you press Share, so it follows the active theme, including the Dark mode switch. "Share day" always covers the whole day, whatever the search box or page is showing. Phones open the share sheet (Save Image, WhatsApp, ...); other devices download `tape-SYMBOL-DATE-HHMM.png` or `tape-day-DATE.png`. To add another kind of card, write another model builder: drawing does not need to change unless it needs a new panel type.


**Calendar event colors and filters:** `lib/events.js` owns the semantic `kindTone()` mapping. The same event tone is used by calendar chips and day-modal rows; CSS custom properties `--event-*` live in `styles/tokens.css`. The Calendar view filters the Fed, Inflation, Jobs and GDP groups using `st.evFilters`; closed days and early closes are session events and always remain visible. `MonthGrid` dims market-closed days and marks early-close days separately. The early-close notice summarizes the uploaded early-close dates and New York close times. Add new event kinds to `KINDS`, `KIND_TONES`, and the matching token/style when extending the event schema.
